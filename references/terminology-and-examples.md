# 용어 선택과 문장 수정 사례

예문은 편집 원칙을 설명하기 위한 가상 문장이다. 특정 프로젝트의 구조나 선호 용어를 전제로 하지 않는다. 예문의 수정안을 다른 문서에 그대로 적용하지 말고 원문이 가진 정보와 문맥을 확인한다.

## 용어 선택 순서

1. 사용자가 지정한 표현이 있는지 확인한다.
2. 문서나 프로젝트에 용어집과 작성 규칙이 있으면 따른다.
3. 같은 개념을 가리키는 기존 표현을 모아 대표 표기를 정한다. 사용 빈도만으로 적절성을 판단하지 않는다.
4. 기준이 없으면 해당 분야의 독자에게 익숙하고 개념을 정확히 전달하는 표현을 고른다. 관용적인 영어 표현을 억지로 번역하지 않고, 자연스러운 한국어를 불필요하게 영어로 바꾸지도 않는다.
5. 근거 없이 특정 표현이 업계 표준이라고 단정하지 않는다. 판단이 어려우면 명확한 기존 표기를 유지한다.

작업용 용어표에는 ‘개념 / 선택한 표기 / 다른 표기 / 예외’를 기록한다. 실제 식별자, 공식 제품명, 인용문은 설명문과 별도로 취급한다. 동의어처럼 보여도 범위나 동작이 다르면 하나로 합치지 않는다.

## 문장 수정 사례

### 추상적인 동작을 구체화하기

수정 전: “설정 변경의 수행이 완료된 이후 재시작의 진행이 필요하다.”

수정 후: “설정을 변경한 뒤 재시작해야 한다.”

명사 나열을 동사로 풀되 ‘재시작이 필요하다’는 의무 수준을 유지한다. 원문에 대상이 없다면 임의의 서비스 이름을 추가하지 않는다.

### 모호한 비유를 실제 관계로 바꾸기

수정 전: “설정값은 여러 곳을 여행한 뒤 화면에 도착한다.”

값이 처리 단계를 거쳐 화면에 표시되는 문맥:

> 설정값은 여러 처리 단계를 거쳐 화면에 표시된다.

구체적인 단계가 원문에 제시되어 있으면 그 이름을 활용한다. 제시되지 않은 네트워크 요청이나 저장 단계를 만들어 넣지 않는다.

### 불필요한 피동을 줄이기

수정 전: “서버에 의해 요청에 대한 검증이 수행된다.”

수정 후: “서버가 요청을 검증한다.”

행위 주체가 명시된 경우 능동문으로 다듬을 수 있다. 주체를 알 수 없는 문장에서는 피동을 없애기 위해 주체를 추측하지 않는다.

### 조건과 보장 수준을 유지하기

수정 전: “일시적인 오류라면 재시도를 통해 요청이 성공할 수 있다.”

수정 후: “일시적인 오류라면 재시도했을 때 요청이 성공할 수 있다.”

부적절한 수정: “오류가 발생해도 재시도하면 요청이 성공한다.”

부적절한 수정은 오류의 범위를 넓히고 성공 가능성을 보장으로 바꾼다. 문장이 유창해져도 의미가 달라지면 채택하지 않는다.

### 유효한 기술 용어를 문맥에 맞게 사용하기

전문 용어 자체가 잘못되지 않았더라도 대상이 모호하면 문맥에 명시된 구성요소나 동작을 쓴다. 반대로 용어가 정확하게 쓰였다면 더 쉬운 표현으로 바꾸려다가 개념의 범위를 넓히지 않는다. 일반어와 전문 용어를 구분하고, 단어 단위의 금지 목록을 만들지 않는다.

## 최종 점검

- 지시 대상이 모호한 ‘이것’, ‘해당 처리’, ‘위 내용’을 문맥만으로 식별할 수 있는가?
- 영문 용어를 바꾼 뒤 조사와 서술어가 자연스럽게 이어지는가?
- 같은 개념의 표기가 본문, 표, 제목, 목차에서 일치하는가?
- 현재 동작, 설계 목표, 제약 조건, 향후 계획이 구분되어 있는가?
- 조건, 예외, 부정, 수치와 단위가 그대로 유지되는가?
- 문체를 다듬는 과정에서 코드, 링크, 식별자나 인용문을 바꾸지 않았는가?
- 이미 명확한 문장을 수정량을 늘리기 위해 바꾸지는 않았는가?
