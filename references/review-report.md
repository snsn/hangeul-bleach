# 상세 분석과 교정 보고

상세 리뷰, 수정 이유, 스타일 분석을 요청받았을 때 이 흐름을 사용한다. 파일을 다듬어 달라는 요청만 있으면 같은 기준으로 내부 검토하되 결과 보고는 짧게 한다. 보고서를 만들기 위해 문서를 불필요하게 고치지 않는다.

## 1. 범위와 문서 성격

검토한 파일·절, 독자, 문서 목적, 기존 문체, 사용자 지정 기준을 기록한다. 목적을 추정했다면 관찰한 근거를 쓴다. 예를 들어 명령어와 API 예제가 많은 문서는 개발자 안내로 볼 수 있지만, 이를 이유로 모든 한국어를 영문으로 바꾸지는 않는다.

인용, UI 문구, 예제, 코드와 일반 설명문을 구분한다. 문서가 짧거나 문맥이 부족하면 판단 가능한 항목부터 처리한다. 모호함이 실제 수정 방향에 영향을 미칠 때만 질문한다.

## 2. 근거 수집

- 파일 경로와 줄 번호 또는 절·문단·표 행으로 위치를 남긴다.
- 용어와 종결형의 사용 분포를 조사할 때 코드·인용문을 포함했는지 명시한다.
- 검색된 문자열을 같은 개념의 용례인지 직접 읽고 분류한다.
- 횟수는 실제 확인했을 때만 쓴다. 확인하지 않았다면 대표 위치만 제시한다.
- 여러 파일을 검토할 때는 같은 개념의 파일 간 충돌과 파일 안의 충돌을 구분한다.

## 3. 발견 사항의 단위

발견 사항 하나는 하나의 판단과 수정 방향이다. 같은 원인으로 여러 위치를 수정하면 하나의 항목 아래 위치를 묶을 수 있다. 한 문장에서 맞춤법과 문체를 각각 고쳤다면 별개 항목으로 기록할 수 있다. 발견 항목 수와 수정 위치 수를 섞지 않는다.

다음 필드를 사용한다.

| 필드 | 기록 내용 |
| --- | --- |
| ID·범주 | 문법 G, 문체 N, 일관성 C 등 문서 안에서 유일한 번호 |
| 위치 | 독자가 원문을 다시 찾을 수 있는 위치 |
| 원문·분포 | 정확한 발췌와 확인된 변형 표기 |
| 판단 | 오류 / 통일 권장 / 문체 제안 / 유지 / 확인 필요 |
| 수정안 | 실제로 적용 가능한 문장 또는 표기 |
| 근거 | 문법 규칙, 사용자 지시, 문서 내 기준, 의미 명료성 등 |
| 예외·보존 | 코드, 인용, 의미 차이 등 함께 바꾸지 않은 대상 |

문법상 틀리지 않은 표현을 ‘오류’로 표시하지 않는다. ‘확인 필요’는 자동 수정 대상이 아니다. 근거로 외부 표준을 인용하려면 실제 조항이나 내용을 확인한다. 기관 이름만 붙여 개인적인 선택을 공식 표준처럼 설명하지 않는다.

## 4. 수정 우선순위

1. 의미가 달라지는 호응·부정·조건·지시 대상 문제와 명백한 맞춤법 오류.
2. 독자가 다른 개념으로 오해할 수 있는 용어 혼용, 깨진 문장·참조.
3. 문장 흐름, 불필요한 반복과 추상 표현.
4. 의미에 영향이 작은 강조·기호·표시 형식.

이 순서는 작업 순서이며 AI 작성 가능성이나 심각도 점수가 아니다. 먼저 고칠 항목이어도 원뜻을 알 수 없다면 확인이 필요하다.

## 5. 결과 구성

상세 보고에는 다음 순서를 권장한다.

1. 검토 범위와 채택한 기준.
2. 범주별 발견 사항: 원문 → 수정안, 근거, 예외.
3. 수정본 또는 수정한 파일 링크. 짧은 텍스트는 전체 수정본을 함께 제공한다.
4. 수정·유지·확인 필요 항목의 요약. 집계했다면 중복 계산이 없는지 확인한다.
5. 이번 문서에 적용한 용어표와 스타일 규칙. 다음 문서에도 강제되는 보편 규칙으로 표현하지 않는다.
6. 의미 보존과 파일 검사 결과, 남은 질문과 미검토 범위.

‘교정 불필요’ 항목은 오류 개수에 넣지 않는다. 이미 일관적인 문서는 그 사실을 알리고 선택적인 개선만 제안한다. 모든 항목이 통과했다고 말하려면 실제로 해당 범위를 확인해야 한다.
